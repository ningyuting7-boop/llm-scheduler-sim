## 0. 一句话结论

在真实 vLLM 上，**按预测长度排序（SJF）把中位排队时间降低了 7.4 倍**（24.4 s → 3.3 s），代价是尾部翻倍；但**论文的核心创新——CVaR 不确定性项——没有带来可测量的额外收益**，而且这不是我们 σ 预测器质量的问题：换成阶段一用 20 次真实采样拟合出的 σ，结果同样没有变化。

## 3. 主结果：SJF 把中位等待降低 7.4 倍，但不减少总等待

### 3.1 rate 16（ρ=1.83）的分布变化

| 臂 | p50 | p90 | p99 | **mean** |
|---|---|---|---|---|
| FCFS + Predictor | 24,382 | 44,025 | 48,081 | 24,514 |
| Predicted-SJF | **3,303** (−86.5%) | 72,928 (+65.7%) | 97,905 (+103.6%) | 25,559 (**+4.3%**) |
| TIE | **3,759** (−84.6%) | 70,155 (+59.4%) | 89,413 (+86.0%) | 24,914 (**+1.6%**) |

FCFS 的三个分位挤在 24–48 秒（等待只取决于到达序号），SJF 则从 3.3 秒铺到 98 秒——**跨度 30 倍**。

### 3.2 为什么 mean 不动：总排队时间守恒

并发被 `max_num_seqs=32` 钉死（而非被显存约束，见 §5），因此 GPU 始终以固定 32 路解码运行，吞吐恒定。总排队时间等于队列长度曲线下的面积，**只取决于到达过程与服务速率，与服务顺序无关**。调度因此只能**重新分配**等待，不能减少。

这有一个直接的方法论后果：

> **在此配置下，只报告 mean TTFT 会把 7.4 倍的改善写成"无效果"（+4.3%）。** 分析脚本的第一版就犯了这个错误，后来补上 p50/p90 才发现主效应。

## 4. 两条可验证的规律

### 4.1 过载时 FCFS 的等待是到达序号的线性函数

ρ>1 时队列线性发散，第 i 条请求的等待为

$$W(i) = i\left(\frac{1}{\mu} - \frac{1}{\lambda}\right)$$

μ = 实际吞吐，λ = 发起速率。与 FCFS 实测对比：

| 负载 | 分位 | 公式预测 | 实测 | 误差 |
|---|---|---|---|---|
| rate 16 | p50 | 24,678 ms | 22,157 ms | +11% |
| | p90 | 44,421 ms | 41,475 ms | +7% |
| | p99 | 48,863 ms | 45,495 ms | +7% |
| rate 32 | p50 | 39,869 ms | 37,129 ms | +7% |
| | p90 | 71,764 ms | 68,590 ms | +5% |
| | p99 | 78,940 ms | 75,672 ms | +4% |

**误差 4–11%。** 所以 p90 TTFT 从 rate 8 的 569 ms 跳到 rate 16 的 41,475 ms 不是异常，而是 ρ 跨越 1 的必然结果。

### 4.2 交叉分位 $p^\* = 100/\rho$

过载时，一个到达窗口内最多只有 $\mu/\lambda = 1/\rho$ 比例的请求能"即到即走"。SJF 的收益正来自让这批短请求插队，其余的无论怎么排都得在积压中等待。因此：

> **SJF 只能改善低于 $p^\*=100/\rho$ 的分位数，高于它的必然恶化。**

| 负载 | ρ | $p^\*$ | p50 | p90 | p99 |
|---|---|---|---|---|---|
| rate 8 | 1.02 | 98 | −2.9% ✓ | −24.5% ✓ | +111.1% ✓ |
| rate 16 | 1.83 | 55 | −86.5% ✓ | +65.7% ✓ | +103.6% ✓ |
| rate 32 | 3.64 | 27 | −3.6% ✗ | +15.5% ✓ | +28.0% ✓ |

**9 个预测中 8 个成立**；唯一不符的（rate 32 的 p50）预测恶化而实测基本持平（−3.6%），处于噪声量级。

这解释了一个反直觉现象：**过载越严重，SJF 的优势越小**。rate 16 效果最戏剧化，正是因为 $p^\*≈55$ 恰好落在中位数附近。

## 5. 机制核查：为什么吞吐五臂一致

从 server 日志中提取排队阶段（`Waiting > 0`）的引擎状态：

| 臂 | Running 均值 | 满编 32 的占比 | Waiting 均值 | KV 用量均值 | KV 峰值 | 抢占次数 |
|---|---|---|---|---|---|---|
| FCFS | 31.60 | 76% | 242 | 2.0% | 2.5% | **0** |
| FCFS+Pred | 31.70 | 74% | 238 | 1.9% | 2.5% | **0** |
| Pred-SJF | 31.77 | 85% | 248 | 2.0% | 2.6% | **0** |
| TIE | 31.81 | 85% | 246 | 1.9% | 2.3% | **0** |
| TIE-oracle | 31.89 | 89% | 237 | 1.9% | 2.3% | **0** |

> 样本量仅 25–27（vLLM 每 ~10 秒打印一次统计），76% 与 85% 的差异**统计上不可靠**，不应作为结论。Running 均值的差异（31.60 vs 31.89）不足 1%。

vLLM 启动时自报：

```
GPU KV cache size: 394,544 tokens
Maximum concurrency for 8,192 tokens per request: 48.16x
```

即使每条请求用满 8192 上下文，显存也支持 48 条并发；按实际平均序列长度 351 tokens 计算则可支持约 **1,124 条**。我们卡在 32，**KV cache 利用率仅 2%**。

因此机制链条完整闭合：

```
max_num_seqs=32 钉死并发
  → 各臂 batch 均跑满 ~31.8/32（差异 <1%）
  → KV 用量均为 2%，零抢占
  → GPU 执行相同的工作量、相同的批大小
  → token 吞吐一致（2,132–2,237 tok/s，跨臂差异 <5%）
  → 总排队时间守恒
  → 调度只能重新分配等待
```

**各臂的差异不在"占了多少槽位"，而在"哪些请求占了这 32 个槽位"。**

### 5.1 GPU 利用率的 roofline 估算

未直接采样 GPU 利用率（疏漏，见 §9）。但可由 TPOT 推算：

| 量 | 值 |
|---|---|
| Qwen3-8B bf16 权重 | 16.4 GB |
| A100-40GB HBM 带宽 | 1,555 GB/s |
| 理论最短 step 时间 | 10.5 ms |
| 实测 TPOT | **14 ms** |
| **显存带宽利用率** | **≈ 75%** |

验算吞吐：32 ÷ 14 ms = 2,286 tok/s，实测 2,237 tok/s，**误差 2%**，模型吻合。

解码阶段是**显存带宽瓶颈**而非算力瓶颈：每个 step 必须读一遍全部权重，与 batch 大小无关。因此 batch 32 时"读 16.4 GB 权重只产出 32 个 token"，SM 大部分时间在等内存。外推：

|---|---|---|---|---|
| **32**（当前） | 18 GB | 14 ms | 2,237 | **8.8** |
| 128 | 23 GB | ~18 ms | ~7,100 | ~28 |
| 512 | 42 GB | ~33 ms | ~15,500 | **~62** |

## 7. 机制：为什么 CVaR 项是近乎冗余的

### 7.1 打分乘子的离散度远小于 E[X]

TIE 打分可写作

$$\text{score} = \mathbb{E}[X]\,(1+\beta r),\qquad r=\frac{\text{CVaR}_{0.9}}{\mathbb{E}[X]}$$

排序由两个因子的**相对离散度**决定。在本 workload 上（p10→p90 跨度）：

| 因子 | 跨度 |
|---|---|
| $\mathbb{E}[X]$ | **48.5×** |
| $(1+\beta r)$，β=0.1 | 1.07× |
| $(1+\beta r)$，β=0.5 | 1.26× |

**E[X] 的话语权是 CVaR 项的 40 倍以上。**

由此可导出换序上界：TIE 要交换 $\mathbb{E}_i<\mathbb{E}_j$ 的两条请求，需要

$$\frac{\mathbb{E}_j}{\mathbb{E}_i}<\frac{1+\beta r_{\max}}{1+\beta r_{\min}}\approx 3.3\times$$

即**只能交换预期长度相差 3.3 倍以内的请求**，而本 workload 的 E[X] 跨度是 48 倍。

### 7.2 根本原因：E[X] 本身已是 σ 的增函数

对数正态族的期望随 σ 单调递增（log-normal 下即 $\mathbb{E}[X]=e^{\mu+\sigma^2/2}$）。因此：

> **按 E[X] 排序的 SJF 本身就是一阶风险感知的。** σ 大的请求，其期望长度已被推高，SJF 自动将其推后。CVaR 项只提供二阶差异。

验证：固定 μ、令 σ 双峰（一半 0.05、一半 1.5），Spearman = **1.0000**——完全一致。因为 μ 固定时按 E[X] 排序已等价于按 σ 排序。

### 7.3 边界条件：TIE 何时才会不同于 SJF

只有当**预期短但风险高**与**预期长但确定**两类请求共存时，均值与 CVaR 才会给出不同排序。决定变量是 $\mathrm{corr}(\mu,\sigma)$：

| Workload | corr(μ,σ) | Spearman | top-32 重叠 |
|---|---|---|---|
| **本实验实测** | **+0.04** | **0.9963** | **94%** |
| μ,σ 独立 | +0.02 | 0.9938 | 88% |
| μ,σ 强反向 | −0.94 | 0.8799 | 53% |
| μ,σ 近乎完全反向 | −0.97 | 0.8109 | 41% |
| 极端：短请求全高风险、长请求全确定 | −1.00 | **−0.6338** | **0%** |

σ 整体放大（2× 至 12×）**无效**——Spearman 始终 ≥0.99，因为 2048 的截断使 E[X] 与 CVaR 一同向上限饱和，比值不再增长。

**因此 TIE 发挥作用需要的 workload 是：**

| 类型 | μ | σ | 例子 |
|---|---|---|---|
| 长但可预测 | 高 | 低 | 定长翻译、"写 500 字…"、结构化生成 |
| 短但会爆 | 低 | 高 | 歧义提问、时而拒答时而长篇、会触发 reasoning 的问题 |

本实验使用的 LMSYS 纯聊天负载任务类型同质，`corr(μ,σ)=+0.04`，恰好落在 TIE 最无效的区域。

**这是负载性质，不是预测器质量问题**——oracle σ 臂给出了同样的结果。

## 9. 与论文的对照

### 9.1 论文的 100 RPS 是发起速率，不是实际吞吐

由论文 Table 3 反推：FCFS 跑完 3,000 条需 229.37 s → **实际吞吐 13.1 req/s**。发起 100 RPS 即**过载 7.6 倍**。我们 rate 32 时实际吞吐 9.01 req/s，过载 3.6 倍——**同一区间，只是标注方式不同**。

13.1 vs 8.8 的差距主要来自平均输出长度（由其 Table 2 反推为 35–97 tokens，我们是 249）与硬件。

### 9.2 论文的 "Per-token Latency" 是归一化延迟

$$\text{PTL}_i=\frac{E2E_i}{N_i}$$

用其自身数据交叉验证（反推输出长度一致）：

| 测试集/模型 | Avg TTFT | Avg PTL | 反推 $N$ |
|---|---|---|---|
| ShareGPT 8B | 161.56 s | 1.66 s/tok | ≈ 97 |
| ShareGPT 8B (P90) | 316.07 s | 3.27 s/tok | ≈ 97 ✓ |
| Alpaca 8B | 83.65 s | 1.45 s/tok | ≈ 58 |
| Alpaca 70B | 235.64 s | 4.52 s/tok | ≈ 52 ✓ |
| LMSYS 70B | 319.51 s | 9.08 s/tok | ≈ 35 |

该指标被 TTFT 完全主导（我们的 TPOT 仅 0.014 s/token，相差 100–600 倍）。

**⚠️ 该指标在结构上偏袒 SJF 类策略。** 分母是输出长度，让短请求等待会被放大惩罚，让长请求等待则被稀释。极端例子——两条请求，10 token 与 1000 token：

| 策略 | 短请求等待 | 长请求等待 | 短的 PTL | 长的 PTL | **平均 PTL** |
|---|---|---|---|---|---|
| FCFS | 100 s | 100 s | 10.0 | 0.1 | **5.05** |
| SJF | 0 s | 200 s | 0.0 | 0.2 | **0.10** |

**总等待完全相同（200 s），归一化延迟差 50 倍。**

因此论文报告的收益应拆为三部分：

| 来源 | 是否真实减少总等待 |
|---|---|
| 归一化指标的结构性偏袒 | ❌ 纯指标效应 |
| 等待在请求间重新分配 | ❌ 守恒，仅分布改变 |
| 吞吐提升（Table 3 的 2.3×） | ✅ 真实，但需显存成为约束 |

### 9.3 本实验的 PTL（聚合近似）

**无法计算论文口径的 PTL**——需逐请求 $E2E_i$ 与 $N_i$，而 `vllm bench serve` 在未加 `--save-detailed` 时会删除这些数组。仅能给出聚合近似 $\overline{E2E}/\bar N$：

| rate | ρ | FCFS | FCFS+Pred | SJF | TIE | TIE-oracle | TTFT 占 E2EL |
|---|---|---|---|---|---|---|---|
| 2 | 1.00 | 0.0119 | 0.0121 | 0.0121 | 0.0121 | 0.0120 | 1% |
| 4 | 1.01 | 0.0124 | 0.0127 | 0.0127 | 0.0127 | 0.0126 | 1% |
| 6 | 1.02 | 0.0132 | 0.0136 | 0.0135 | 0.0137 | 0.0136 | 1% |
| **8** | 1.02 | **0.0143** | **0.0153** | **0.0153** | **0.0152** | **0.0150** | 7% |
| 16 | 1.83 | 0.1055 | 0.1131 | 0.1173 | 0.1146 | 0.1137 | 87% |
| 32 | 3.64 | 0.1653 | 0.1737 | 0.1720 | 0.1709 | 0.1728 | 92% |

由 Jensen 不等式，$\overline{E2E}/\bar N < \overline{(E2E/N)}$，且我们的 $N$ 跨度很大（p10≈27 至 p90≈1305），真实均值可能大一个数量级。**上表中 SJF 与 FCFS 看似接近是近似造成的假象**——它恰好抹掉了该指标偏袒 SJF 的效应。

## 10. 局限与下一步

### 10.1 `max_num_seqs=32` 的双刃性

该配置沿用自 TIE 的 `start-server.sh`（B 需与 β 公式一致）。经核验，它使并发受**配置**而非显存约束（KV 利用率 2%，抢占 0 次）。

- **优点**：排除了抢占这一混杂因素，各臂唯一差异就是准入顺序
- **代价**：同时**排除了显存压力通路**——即调度通过降低 KV 占用提升并发与吞吐的机制

因此本实验测量的是"调度如何**重新分配**等待"，而非"调度能否**减少**总等待"。论文报告的吞吐增益属于后者，在本配置下**结构性地不可能复现**。

> 注意 vLLM 官方默认为 `max_num_seqs=128`，TIE 调低至 32。这是一个**承重假设**：batch 越小，队列越早排满，调度器才有事可做。

### 10.2 其他局限

| 局限 | 影响 |
|---|---|
| 未加 `--save-detailed` | 无法计算论文口径的 PTL 及其分位数 |
| rate 8（ρ=1.02）与 rate 16（ρ=1.83）之间未采样 | 真实服务最常处于的区间缺失 |
| 未采样 GPU 利用率 | §5.1 的 roofline 分析为推算，未实测 |
| 仅一种 workload | §7.3 的 `corr(μ,σ)` 边界条件仅有离线排序分析，无端到端验证 |

### 10.3 建议的补充实验

```bash
sbatch --export=ALL,MAX_NUM_SEQS=512,ARMS="fcfs_pred sjf tie",REQUEST_RATES="32 64 100" \
       --time=02:30:00 hpc/benchmark_serving.slurm
```

一次可回答三件事：

1. **论文口径的 PTL**（`--save-detailed` 已加入脚本）
2. **放开并发后吞吐增益能否复现**——按 §5.1 外推，`max_num_seqs=512` 时饱和点约 62 req/s
3. **与论文可比的 RPS 量级**——100 RPS 将仅为 1.6 倍过载

> ⚠️ `max_num_seqs=512` 时 β 公式中的 B 也随之变为 512（`vllm_tie/scheduler.py` 从 `self.max_num_running_reqs` 读取），队列需深至 2,560 才能使 β 触顶。**这与论文 B=32 的设定差异很大，该组数据与主实验不可直接比较**，报告中须注明。

## 11. 结论

1. **在真实 vLLM 上，按预测长度排序确实有效**：ρ=1.83 时中位排队时间降低 **7.4 倍**（24.4 s → 3.3 s）。
2. **但收益是分布性的，不是总量性的**：并发受配置约束时总排队时间守恒，mean TTFT 仅 +4.3%，收益全部来自把等待从中位数搬到尾部（p99 +103.6%）。
3. **SJF 的收益存在负载窗口**：只能改善低于 $p^\*=100/\rho$ 的分位数，过载越重受益比例越小。
4. **TIE 的 CVaR 项在本 workload 上没有可测量的贡献**，且该结论在 oracle σ 下依然成立——**是负载性质，不是预测器质量**。
5. **机制已被定位**：对数正态族的 E[X] 本身随 σ 单调递增，SJF 已隐式完成一阶风险规避；CVaR 项仅在 `corr(μ,σ)` 显著为负时才提供额外信息。
6. **预测器的部署开销被量化**：TPOT +2~5%、吞吐 −2%，这是论文未报告的数字。
7. **论文指标存在结构性偏袒**：归一化延迟 $E2E/N$ 会在总等待不变的情况下放大 SJF 的表观优势数十倍。
