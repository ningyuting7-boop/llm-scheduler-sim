# 阶段二:训练 DeBERTa 长度预测器

## 背景与目标

阶段一已经产出 `data/qwen3_8b_logt_labels.csv`——9,998 条真实的 `(prompt, logt_mu, logt_sigma)` 数据(来自 Qwen3-8B 在 LMSYS-Chat-1M 前 9,998 条 prompt 上的真实采样与 log-t 拟合)。阶段二要在这份数据上微调一个 **DeBERTa-v3-base** 模型,让它学会:给定一个新 prompt,直接预测出 `(μ̂, σ̂)`,供阶段三的 TIE scheduler 在真实 serving 时打分用(`score = E[X] + β·CVaR_0.9[X]`)。

这一步完全是**本地/单卡任务,不需要在 HPC 上排队**——DeBERTa-v3-base 只有 ~184M 参数,训练显存需求远低于阶段一跑 Qwen3-8B 生成时用到的量级,一张 A100(甚至一张普通消费级 GPU)都绰绰有余。

---

## 关键设计决定及理由

### 1. 模型结构:复用 TIE 官方预测器的架构

```
prompt 文本
   ↓ DeBERTa-v3-base encoder(12层 Transformer,hidden=768)
   ↓ multi-pooling:[CLS 向量, 全 token mean pool, 全 token max pool] 拼接
     → 768×3 = 2304 维特征
   ↓ 两个独立分支(分别预测 μ 和 σ):
     每条分支:Linear→LayerNorm→GELU→Dropout(0.2),重复 2 次,hidden=256
     ↓ 回归头:Linear(256→128)→GELU→Dropout(0.1)→Linear(128→1)
   → 输出两个标量:μ̂, σ̂
```

**为什么这么设计(不是随便抄的)**:
- **Multi-pooling 而不是只用 CLS**:CLS 向量单独训练容易丢信息,拼上 mean/max pool 能让模型同时看到"整体语义倾向"(mean)和"最突出的局部信号"(max,比如 prompt 里某个强烈暗示"要写很长"的关键词),这对预测一个**分布形状**(不只是一个点)是有意义的先验
- **μ、σ 用两个独立分支,不共享最后几层**:这两个量的性质完全不同(μ 是"大概多长",σ 是"我对这个判断有多不确定"),强行共享最后的回归头会让两个任务的梯度互相干扰
- **微调整个 encoder,不冻住**(2026-08-21 已确认):数据量(9,998 条)对一个 86M 参数的 encoder 做微调是足够的,而且预测"输出长度的分布特征"这个任务,和 DeBERTa 预训练时的通用语言理解任务差异不小,冻住 encoder 只训后面几层 MLP,表达能力会明显打折

### 2. `max_length = 512`,不是可调超参数,是硬限制(2026-08-21 确认)

查了 DeBERTa-v3-base 的 config:`max_position_embeddings = 512`。它的位置编码不是 RoPE(旋转、连续函数,能通过插值优雅扩展),而是**学出来的、按相对距离分桶的 embedding 表**(`position_buckets=256`)——桶对应的向量是训练时学出来的离散参数,没见过的桶(超过 512 才会用到)完全没训练过,插值没有数学上的正当性,真要扩展等于要做一次不小的"模型手术"。所以 512 不是 TIE 作者"选"的,是这个模型架构的天花板,我们**没有别的选项**。

**结合我们自己数据的 token 长度分布**(用真实 DeBERTa tokenizer 测的,9,998 个 prompt):

```
中位数 25,p75=77,p90=258,p95=371,p99=671,max=1794
≤512 token 覆盖 97.6%
```

512 覆盖了 97.6% 的 prompt,剩下 ~2.4%(主要是带 few-shot 例子的长指令类 prompt)会被截断——这是模型架构限制带来的、可接受的已知损失,不是我们工程决策的失误。

**顺带修了 TIE 仓库自己的一个 bug**:他们训练用 512、推理(`ua_predictor.py`)用 2048——推理那边如果真收到一个 512-2048 token 之间的长 prompt,会因为超出位置编码范围直接报错崩溃,不是"效果差",是"跑不起来"。我们训练和(未来阶段三)推理都统一用 512,从根上避免这个问题。

### 3. 标签归一化:z-score(μ)+ log1p 再 z-score(σ)

- `μ` 本身量级还行(大概 0-8),直接 z-score 标准化
- `σ` 大部分很小、少数很大(分布本身右偏,类似我们之前发现的"内部波动"现象——大多数 prompt 的 σ 很小、一小撮 prompt 的 σ 很大),直接标准化容易被少数极端值主导训练;先 `log1p` 压缩量级、再 z-score,让优化目标更平滑
- 归一化用的 `(mean, std)` 必须存下来(`normalize_stats.json`),推理时用同一套参数反归一化——这也是 TIE 原代码的做法,不存的话训练和推理就对不上

### 4. Loss:两个头分别算 MSE,等权重求和

`loss = loss_mu + loss_sigma`(两者都已经是 z-score 后的标准化目标,量级天然接近,不需要像 TIE 原代码那样再引入一个额外的、需要手动调的 `sigma_weight`)——这是相对于 TIE 原实现的一个**刻意简化**:他们的 `sigma_weight` 是动态/可调的,我们目前没有掌握他们具体的调整策略,等权重是一个更简单、有清晰理由(两个目标都已标准化)的替代方案,以后如果发现某个头训练明显滞后,再针对性加权。

### 5. 训练配置

| 项 | 值 | 理由 |
|---|---|---|
| Optimizer | AdamW,lr=2e-5,weight_decay=0.01 | 微调预训练 encoder 的标准学习率量级,不宜过大破坏预训练权重 |
| LR schedule | linear warmup(前 10% 步数)+ linear decay | 微调 transformer 的标准做法,避免训练初期大梯度冲击预训练权重 |
| Batch size | 32 | 与 TIE 一致,这个数据规模下合理 |
| Epochs | 20,配合 early stopping(val loss 不再降就停) | 防止在 9,998 条数据上过拟合 |
| Train/Val/Test | 60% / 20% / 20%(两阶段切分) | 与 TIE 一致;test 集留到最后评估用,训练/调参阶段不碰 |
| 加权采样 | `WeightedRandomSampler`,对高 σ / 极端 μ 的样本加权(1.5x/2x) | 我们自己的数据分析已经证实:~4-5% 的 prompt 是"高不确定性"的少数类(roleplay、NSFW 相关、强格式约束这些),这些恰恰是 TIE 的 CVaR 机制最需要预测器能分辨出来的对象——如果训练时不特别照顾这批少数样本,模型很容易被占多数的"正常"样本主导,学不好这批真正重要的少数类 |

### 6. 输出产物

- 模型 checkpoint(encoder 权重 + 两个 MLP 头)
- `normalize_stats.json`(μ 的 mean/std,σ 的 log1p-mean/std)
- 训练日志(train/val loss 曲线,方便看有没有过拟合)

## 验证计划

1. **本地(这台 Mac,不需要 GPU)**:用一个随机初始化的迷你 DeBERTa config(比如 2 层、hidden=64)跑通整个前向传播 + loss 计算 + 一步梯度更新,确认代码逻辑没问题——这一步的重点是抓"维度不对"、"归一化写反"这类逻辑 bug,不是训练出真正有用的模型
2. **HPC 上小规模测试**:用真实 DeBERTa-v3-base + 真实数据的一个小子集(比如 200 条),跑 1-2 个 epoch,确认能真正下载模型、真实数据 pipeline 没问题、loss 会下降
3. **HPC 上正式训练**:全部 9,998 条,20 epoch + early stopping

## 已知局限(训练数据)

1. **`src/logt_fit.py` 的退化样本判断曾经是个 bug,已修复,标签已重新生成**:原代码用 `sample_std == 0.0` 判断"20 次采样是否完全相同",但 `np.std` 对完全相同的浮点数几乎从不返回精确的 `0.0`(会有 ~1e-16 量级的浮点噪声),导致这个判断从未触发过,优化器在这类退化场景里会把 σ 拟合到接近 0 而不是设计好的 0.05 下限。进一步排查发现即使不是完全退化(比如 20 次里 15 次撞到同一个值、5 次不同),`nu=3.5` 的重尾似然也会让优化器倾向于把 σ 收得过小、把真实的离散度甩锅给重尾分布解释。已修复(阈值改用 `<1e-8`、给 L-BFGS-B 加下界、拟合后跟原始样本标准差做合理性检查,不合理则回退到修正后的矩估计),受影响的约 1561/9998(15.6%)行已用修复后的代码重新拟合,`data/qwen3_8b_logt_labels.csv` 已更新。
2. **右截断(censoring)**:延续 Phase 1(`docs/VLLM_Qwen3_Reproduction_Plan.md`)已经记录的已知限制——`max_tokens=2048`(与 TIE 论文自己的截断常数对齐)导致 ~4-9% 的 prompt 至少有一次采样精确撞到这个上限,这些观测值的真实长度是"≥2048,未知具体多少",不是精确值。当前的 `fit_logt` 把它们当精确值处理,没有做正式的截断似然建模——**故意不丢弃这批 prompt**,因为它们恰好是输出最长的一批,丢掉会直接砍掉训练数据里最长尾的部分,而这正是 TIE 的 CVaR 机制最需要预测器认识的对象。当前处理方式是纯粹的近似,以后如果发现预测器在长输出 prompt 上系统性表现差,应该回来实现正式的截断似然,而不是拿掉数据。
3. **重复 prompt 的 train/val/test 泄漏风险**:9998 行里有 205 个 prompt 文本重复出现(共 1122 行,~11%),按行随机切分会让同一个 prompt 同时出现在训练集和验证/测试集里。`scripts/train_predictor.py` 的切分逻辑改成按去重后的 prompt 分组切,保证同一个 prompt 的所有行整体分到同一个 split。
4. **KS 拟合优度检验的样本量比论文小,通过率不能直接对比论文数字**:论文每个 prompt 采样 100 次算 KS 检验,我们受算力限制只采了 20 次,检验功效(power)更低,更难探测出真实是重尾分布但被误判成正态这种细微偏差。用修复后的标签重新跑 `scripts/ks_pass_rate.py`:log-t 通过率 90.3%(论文 93.1%,接近),log-normal 通过率 84.7%(论文 60.3%,高出很多)——log-t 依然是更优选择,但优势幅度比论文小,原因是采样预算不同,不是模型选择错误,报告里不能直接引用论文的 93.1%/60.3% 当成我们自己的结果。
