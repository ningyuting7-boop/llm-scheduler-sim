# 项目面试手册：LLM 推理调度的不确定性感知

> 用法：第 1 节背熟，第 2–4 节理解到能画出来，第 5–7 节是面试官最爱挖的地方，第 8 节是被 challenge 时的应答，第 9 节是**不许硬编**的清单。

---

## 1. 开场陈述

### 30 秒版

> 我复现并扩展了 ICML 2026 的一篇 LLM 推理调度论文。它的核心想法是：如果能预测每个请求会生成多长，就能用最短作业优先来降低排队延迟；而且因为预测有不确定性，应该用 CVaR 对"可能很长"的请求加罚。
>
> 我做了三件事：用 Qwen3-8B 采样建了带不确定性的标签集、训了一个从 prompt 预测长度分布的模型、把调度器挂进真实 vLLM 做了端到端压测。
>
> **结论是：按预测长度排序确实有效——中位排队时间降低 7.4 倍；但论文的核心创新 CVaR 项，在我的负载上没有可测量的贡献。而且我能证明这不是我预测器不行的问题。**

### 2 分钟版（加这三段）

**为什么能证明不是预测器的问题**：我设计了五个对照臂，其中一臂用的是阶段一通过 20 次真实采样拟合出来的 σ，也就是 oracle 质量的不确定性。它和用预测 σ 的结果一样，都是噪声量级。

**机制是什么**：对数正态族的期望本身就是 σ 的增函数，所以按期望长度排序的 SJF **已经隐式完成了一阶风险规避**。CVaR 项只提供二阶差异，只有在"预期短但风险高"和"预期长但确定"两类请求共存时才有信息量——也就是 μ 和 σ 负相关的负载。我的 LMSYS 聊天负载 corr(μ,σ) = +0.04，恰好落在它最无效的区域。

**我还发现了什么**：我在跑实验之前就用标签直接算出了这个结论——TIE 的排序和纯期望排序的 Spearman 是 0.9963，队头 32 条重叠 94%。真机结果和这个离线预测完全一致。

## 2. 项目全貌

```
阶段一  标签生成
  LMSYS-Chat-1M prompt[0:10000]
    → Qwen3-8B 每条采样 20 次（官方非思考模式参数）
    → 拟合 log-t(μ, σ, ν=3.5)
    → 9,998 条 (prompt, μ, σ)

阶段二  预测器
  DeBERTa-v3-base
    → 多池化 (CLS + masked mean + masked max) = 2304 维
    → 两条独立 MLP 分支
    → (μ̂, σ̂)
  结果：μ R² = 0.7668，σ R² = 0.0501

阶段三  真机基准
  官方 vLLM 0.11.1 + --scheduler-cls 外挂
    → 5 个调度臂 × 6 个到达率 × 1000 条 = 30 轮，0 失败
    → A100-40GB，Qwen3-8B
```

### 为什么选 log-t 而不是 log-normal

输出长度是右偏的，对数后仍有重尾。t 分布（ν=3.5）比正态有更厚的尾，KS 检验通过率更高。ν 固定而非学习，是为了让 μ、σ 两个参数可解释、可比较。

### TIE 打分公式

$$\text{score} = \mathbb{E}[X] + \beta \cdot \text{CVaR}_{0.9}[X], \qquad \beta = \text{clip}\!\left(\frac{0.1 L_q}{B},\, 0.1,\, 0.5\right)$$

- $L_q$ = 当前等待队列长度，$B$ = `max_num_seqs`
- 分数**越低越先调度**
- 两项都在 2048 token 处截断（因为 vLLM 的 `max_tokens` 上限，超出部分不占 GPU）
- β 自适应的含义：队列浅时没必要防尾部风险，队列深时才值得对冲

## 3. 阶段一深挖

### Q：你的标签是怎么来的？为什么是 20 次？

每条 prompt 用 Qwen3-8B 的官方非思考模式参数（temperature 0.6, top_p 0.95, top_k 20）采样 20 次，记录输出长度，再用 MLE 拟合 log-t。

20 次是算力和标签质量的折中。**我后来量化了这个折中**：用分半信度（split-half reliability）测得 σ 标签的 $r^2 = 0.6031 \pm 0.0285$，经 Spearman-Brown 校正后为 0.8740；μ 是 0.9950。所以 σ 标签确实比 μ 噪声大，但远没到不可学的程度——这个数字后来成了关键证据。

### Q：讲一个你修过的 bug

**这是我最喜欢的一个，因为它的 guard 写了但从来没生效过。**

`src/logt_fit.py` 里有个退化检测：如果 20 次采样长度完全相同，σ 应该是 0，直接返回不做优化。

```python
if np.std(np.log(lengths)) == 0.0:   # 永远不会成立
    return degenerate_fit(...)
```

问题：`np.std` 对一组数值完全相同的浮点数返回的是 **~4.44e-16，不是精确的 0.0**。浮点累加误差。所以这个分支一次都没进去过，**9,998 条里有 1,228 条（12.3%）走错了路径**。

查的时候我还发现了第二个独立的问题：另有 **214 条（2.1%）**采样确实有分散度，但拟合出的 σ 接近 0。最糟的一条 `raw_std = 0.2091` 拟合成了 `7.59e-06`。这是重尾分布 MLE 的病态——t 分布可以用极小的 σ 配合极端 t 值来"解释"离群点。

**三部分修复**：

```python
_DEGENERATE_STD_THRESHOLD = 1e-8              # 1. 阈值，不用 == 0
_MIN_LOG_SIGMA = math.log(0.01)               # 2. 给优化器下界
_MIN_FIT_TO_RAW_STD_RATIO = 0.1               # 3. 事后兜底

result = optimize.minimize(..., method="L-BFGS-B",
                           bounds=[(None, None), (_MIN_LOG_SIGMA, None)])
if nu > 2 and sigma_hat < sample_std * _MIN_FIT_TO_RAW_STD_RATIO:
    sigma_hat = sample_std * math.sqrt((nu - 2) / nu)   # 矩估计
```

重新拟合改变了 **1,561 条**。同样的 `== 0.0` 还出现在 `scripts/ks_pass_rate.py` 里，一并修了。

**这个 bug 的危害**：σ=0 意味着 CVaR=E[X]，尾部项完全退化。如果不修，12% 的训练标签是错的，而且**模型会学到"很多 prompt 的不确定性是 0"这个假事实**。

### Q：2048 这个截断是怎么来的？会不会丢信息？

采样时设了 `max_tokens=2048`，所以被截断的样本其真实长度是未知的（右删失）。

我的处理是在**打分**阶段也截断——`E[min(X, 2028)]` 和 `CVaR` 截断在 2048。理由是：**一条本该生成 10,000 token 的请求，实际也只会占用 GPU 2048 个 token 的解码时间**。用未截断的期望给它打分会高估它的阻塞程度。

代价是：σ 很大时 E[X] 和 CVaR 会一起向上限饱和，比值不再增长。我在阶段三实测过这个效应——σ 整体放大 12 倍，排序一致性仍 ≥0.99，正是因为截断。

## 4. 阶段二深挖

### Q：为什么用多池化而不是只用 CLS？

CLS 表示整体语义倾向，但会丢失局部最强信号。预测长度分布时，prompt 里一个短语（"详细解释"、"列出所有"）可能强烈暗示长回答——这种信息 max-pooling 保留得更好。三种拼起来 768×3 = 2304。

### Q：为什么 μ 和 σ 用两条独立分支而不是共享主干？

它们衡量的是不同的东西："多长" vs "我有多不确定"。共享末端层会让两者的梯度互相干扰。这个设计后来也被单任务消融验证了——`mu_weight=0` 只训 σ，R² 依然是 0.03，说明**不是多任务干扰的问题**。

### Q：σ 的 R² 只有 0.05，你排除了哪些解释？

这是整个阶段二最有价值的部分，因为**我差点就得出了错误结论**。

| 假设 | 怎么测的 | 结果 |
|---|---|---|
| 标签噪声太大 | 分半信度 + Spearman-Brown | **推翻**：$r^2$=0.60，SB=0.87，天花板远高于 0.05 |
| 损失权重失衡 | σ权重 1.0 / 2.0 / 3.0→4.0 + 梯度裁剪 | 无改善，2.0 反而更差（R²=0.014） |
| 过拟合 | 第 2 epoch 冻结 encoder，lr→5e-5 | 机制上生效（可训参数降到 1.38M，train_loss 平台期，val 1.3021 vs 1.3602），但 σ 不变 |
| 多任务干扰 | `mu_weight=0` 单训 σ 头 | σ R²=0.0316，没变好 |
| 监控指标被污染 | 引入固定的 `MONITORING_SIGMA_WEIGHT=1.0` | **我的假设被证伪**，修对了但结果没变 |

**诚实地说**：在做分半信度之前，我准备建议"σ 学不了，是标签噪声"。那个测试推翻了我自己的判断。剩下没排除的是数据规模和架构。

### Q：训练时遇到的工程问题

**两次 CUDA OOM**。第一次是 `padding="max_length"` —— 每条 prompt 都补到 512，而**中位 prompt 只有 25 个 token**，98% 的计算在算 padding。

改成动态 padding 后**又 OOM 了一次**，报错一模一样。原因：一个 batch 里只要有一条长 prompt，整批还是要补到接近 512，而固定 seed 的 sampler 又抽到了同一个倒霉 batch。

最终解法：`--batch-size 8 --grad-accum-steps 4`，等效 batch 32，但显存里一次只有 8 条。

另外把 tokenize 从 `__getitem__` 挪到了 `collate_fn` 做批量化，**并验证了改动前后 loss 逐位相同**。

### Q：你的实现和参考实现有什么不同？

我读过作者公布的 `train/model_train.py` 和四个调度文件。差异分三类。

**一、我修掉的方法学问题**

| 项 | 参考实现 | 我的实现 |
|---|---|---|
| 数据切分 | `train_test_split(df, test_size=0.4)`，**按行切，不去重** | **按唯一 prompt 文本分组切分** |
| 随机种子 | `RANDOM_SEED = random.randint(0, 10000)`，**每次运行都不同** | 固定 |
| 打分随机性 | 蒙特卡洛用全局 numpy RNG | 独立 seeded 生成器（`TIE_SCORE_SEED`）|
| β 公式的 B | 独立环境变量 `UA_GPU_BATCH_SIZE`，可能和服务端 `--max-num-seqs` 不一致 | 从 `self.max_num_running_reqs` 实时读取，不可能漂移 |

**数据切分那条有实际后果**：我的数据集 9,998 条里有 **917 条重复 prompt**（唯一 9,081 条，重复率 9.2%）。按行切分会让同一条 prompt 同时落进 train 和 test。

**种子那条**意味着他们每次训练的切分都不同，单次结果无法复现，跑两次也无法比较。

**二、我们独立收敛到同一个做法**

他们的验证损失用的是 `loss_mu + loss_sigma`（不加权），而训练用的是 3→4 的动态 σ 权重。我在自己的代码里也发现并修了这个问题（引入 `MONITORING_SIGMA_WEIGHT = 1.0`）——**如果监控指标跟着训练权重变，你分不清模型变好了还是权重变了**。

**三、他们有而我没采用的**

`compute_sample_weights()` 用绝对阈值上采样尾部：

```python
weights[df['logt_mu'] > 5.5] = 1.5
weights[df['logt_sigma'] > 1.0] = 1.5
weights[(df['logt_mu'] > 6.0) | (df['logt_sigma'] > 1.3)] = 2.0
```

我没用，因为**这些阈值是针对他们的标签分布硬编码的**——见 §7.4，它们在我的数据上几乎不命中。

**其他超参我是对齐的**：`MAX_LENGTH=512`、`LR` 2e-5→5e-5、σ 权重 3→4 线性、`clip_grad_norm_(1.0)`、μ 用 z-score / σ 用 log1p+z-score。编码器冻结时机不同——他们 20 epoch 里第 12 个冻结，我在第 2 个（因为我的数据量小得多，更早过拟合）。

### Q：怎么防止数据泄漏？

数据集里有重复的 prompt 文本。按行切分会让同一条 prompt 同时出现在 train 和 test。所以实现了 `grouped_split()`——**先按唯一 prompt 文本分组，在 prompt 层面切分，再展开回行**。

## 5. 阶段三深挖（面试重点）

### Q：你怎么把自己的调度器接进 vLLM 的？

论文作者给的是一整棵 vLLM fork。照搬要从源码编译 CUDA kernel，在共享集群上风险很高。

但 vLLM 官方自带可插拔调度器：

```python
# vllm/config/scheduler.py:129
scheduler_cls: str | type[object] = Field(default=None)
```

命令行 `--scheduler-cls mod.MyScheduler`，用 `resolve_obj_by_qualname` 动态导入。

`SchedulerInterface` 有 13 个抽象方法，从零实现不可能。但不需要——**继承官方 Scheduler，只替换 `self.waiting` 一个成员**：

```python
class TIEScheduler(Scheduler):
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)        # 官方逻辑原样跑完
        self.waiting = TIERequestQueue(...)      # 唯一的改动
```

对照 fork 的 `Scheduler.__init__`，作者的实质改动也正是这一件事。于是 `pip install vllm==0.11.1` 官方 wheel，不编译，风险清零。

**代价**：`SchedulerInterface` 官方标注为非公开 API（加载时会打印兼容性警告），所以版本必须锁死。

### Q：队列是什么数据结构？复杂度？

**最小堆 + 惰性删除（版本号）**：

```
堆元素 = (effective_score, arrival_time, version, req_id, request)
```

| 操作 | 复杂度 | 实现 |
|---|---|---|
| `peek` | O(1) 摊还 | 从堆顶丢弃过期项直到遇到有效项 |
| `push` | O(log n) | 标准 heappush |
| `pop` | O(log n) 摊还 | 同 peek，丢弃过期项 |
| **`update`** | **O(log n)** | 压入新版本号的新项，旧项自动失效 |
| **`remove`** | **O(1)** | 只删版本号记录，堆里的项留给后续 pop/peek 清理 |

**为什么要惰性删除**：预测是异步的，分数会后到。如果用"找到旧元素并修改"的方式更新，需要 O(n) 查找或额外的索引结构。版本号让更新退化成一次 push。

`arrival_time` 作为第二排序键，保证**分数相同时退化为 FCFS**——这在刚启动、所有请求都还是占位分 2048 的时候很重要。

**防饥饿**：每 5 秒全量重建堆，`effective = base × γ^(tw/τ)`，γ=0.9，τ=30s。这是 O(n)，但跑在后台线程上，**不在每请求的调度路径上**。

### Q：预测在关键路径上吗？

**不在**。这是个常见误解。

```python
def add_request(self, request):
    initial_score = 2048.0                      # 占位分，立即入堆
    heapq.heappush(self._heap, (initial_score, ...))
    self._prediction_queue.put(request)         # 丢给后台线程，立即返回
```

后台 daemon 线程攒批（8 条或 3ms）→ DeBERTa forward → 蒙特卡洛算 E[X]/CVaR → 通过版本号惰性更新堆。**调度主循环从不阻塞等待预测。**

实测预测批延迟 **44.8–48.3 ms/批**。

### Q：怎么知道预测真的及时到达了？

我加了一个计数器 `popped_before_prediction`——**被调度走时还没拿到分数的请求数**。这是个静默失败模式：如果预测总是晚到，队列实质在跑 FCFS，但延迟数据看起来完全正常。

分阶段统计：

| popped 区间 | 未打分占比 | 队深 |
|---|---|---|
| 0–2,115（低负载） | **100%** | 0 |
| 3,727–4,243 | 38% | 188 |
| 4,243–5,836（高负载） | **0–6%** | 170–708 |

低负载 100% 未打分不是问题——**队列是空的，根本没有调度决策可做**。队列一深，几乎所有请求都及时拿到了分数。

## 6. 实验设计（面试官会特别欣赏这块）

### Q：你设计了几个对照臂？每个隔离什么？

五个，**每个相对相邻臂只改变一个变量**：

| 臂 | 相对前一臂改变了什么 |
|---|---|
| ① FCFS | — |
| ② FCFS + Predictor | **加载并运行预测器，但丢弃结果** |
| ⑤ Predicted-SJF | **队列按 E[X] 排序**（`TIE_BETA=0`）|
| ③ TIE | **加上 β·CVaR 项** |
| ④ TIE-oracle | **σ 换成真实拟合值** |

| 对比 | 测出什么 |
|---|---|
| ② − ① | 预测器的**部署开销** |
| ⑤ − ② | **SJF 排序的收益**（GPU 负载完全对等）|
| ③ − ⑤ | **CVaR 项的净贡献**（= 论文的创新点）|
| ④ − ③ | σ 预测质量的**天花板** |

**②、⑤ 这两臂是我加的，论文没有。**

- **②** 让 TIE 臂和基准的 GPU 负载完全对等（都加载 DeBERTa、都跑预测），把"调度决策的收益"和"预测器的开销"分离。这让**单卡部署的结论依然成立**，省掉了争取第二张 GPU 的排队风险。
- **⑤** 是在跑实验前发现必须加的（见下）。没有它，TIE 赢了也分不清是 SJF 赢的还是不确定性感知赢的。

### Q：你说实验前就预测到结果了？

对。我写了 `scripts/rank_agreement_check.py`，**用阶段一的 oracle 标签直接算 TIE 排序和纯 E[X] 排序的一致性**：

| β | Spearman | top-32 队头重叠 |
|---|---|---|
| 0.1（下限） | **0.99957** | 96.9% |
| 0.5（上限） | **0.99625** | 93.8% |

top-32 正好是一批要调度的量，只有 1–2 个位置不同。**两个策略排出的队几乎一样，端到端结果自然也一样。**

这个计算花了十分钟，**在消耗任何 GPU 时间之前**就告诉我：必须加 ⑤ 臂，否则实验无法归因。

### Q：结果是什么？

**rate 16 req/s（ρ=1.83）**，相对 FCFS+Predictor：

| 臂 | p50 TTFT | p90 | p99 | **mean** |
|---|---|---|---|---|
| FCFS + Predictor | 24,382 ms | 44,025 | 48,081 | 24,514 |
| Predicted-SJF | **3,303 ms (−86.5%)** | +65.7% | +103.6% | **+4.3%** |
| TIE | 3,759 ms (−84.6%) | +59.4% | +86.0% | +1.6% |

**中位排队时间降低 7.4 倍，但平均值几乎不动。**

## 7. 机制分析（最能体现深度的部分）

### Q：为什么 mean TTFT 不动？

**总排队时间守恒。**

并发被 `max_num_seqs=32` 钉死（不是被显存），所以 GPU 始终以固定 32 路解码运行，吞吐恒定。总排队时间等于队列长度曲线下的面积，**只取决于到达过程和服务速率，与服务顺序无关**。

调度因此只能**重新分配**等待，不能减少。中位数省下的 21 秒被搬到了尾部（p99 从 48s 涨到 98s）。

**方法论教训**：我的分析脚本第一版只打印 mean 和 p99，**把 7.4 倍的改善报告成了"无效果"（+4.3%）**。补上 p50 才发现主效应。

### Q：你怎么证明并发是被配置而不是被显存卡住的？

四条证据：

```
GPU KV cache size: 394,544 tokens
Maximum concurrency for 8,192 tokens per request: 48.16x
```

1. **KV 利用率 2%**（实测均值 1.9–2.0%，峰值 2.6%）。平均序列 351 token，理论能装 1,124 条
2. **即使每条用满 8192 上下文，显存也支持 48 条** > 我们的 32
3. **抢占次数 = 0**，五个臂全是 0
4. **batch 占用率 31.6–31.9 / 32**，跨臂差异 < 1%

于是机制链条闭合：

```
max_num_seqs=32 钉死并发
  → 各臂 batch 都跑满 ~31.8/32
  → KV 用量 2%，零抢占
  → GPU 做同样的工作、同样的批大小
  → token 吞吐一致（2,132–2,237 tok/s，差异 <5%）
  → 总排队时间守恒
  → 调度只能重新分配等待
```

**各臂的差异不在"占了多少槽位"，而在"哪些请求占了这 32 个槽位"。**

### Q：为什么 CVaR 项没用？

**两层解释。**

**第一层：量级。** 打分可写成

$$\text{score} = \mathbb{E}[X]\,(1+\beta r), \qquad r = \frac{\text{CVaR}_{0.9}}{\mathbb{E}[X]}$$

排序由两个因子的相对离散度决定（p10→p90）：

| 因子 | 跨度 |
|---|---|
| $\mathbb{E}[X]$ | **48.5×** |
| $(1+\beta r)$，β=0.1 | 1.07× |
| $(1+\beta r)$，β=0.5 | 1.26× |

**E[X] 的话语权是 CVaR 项的 40 倍以上。** 由此可导出换序上界：TIE 只能交换预期长度相差 **3.3 倍以内**的请求，而负载的 E[X] 跨度是 48 倍。

**第二层（更深）：冗余。** 对数正态族的期望本身随 σ 单调递增（$\mathbb{E}[X]=e^{\mu+\sigma^2/2}$）。所以：

> **按 E[X] 排序的 SJF 本身就是一阶风险感知的。** σ 大的请求，期望长度已被推高，SJF 自动把它推后。CVaR 项只提供二阶差异。

我验证过：固定 μ、令 σ 双峰（一半 0.05、一半 1.5），Spearman = **1.0000**，完全一致。

### Q：那什么负载下 TIE 才会赢？

只有"预期短但风险高"和"预期长但确定"两类请求共存时，均值和 CVaR 才会给出不同排序。决定变量是 $\mathrm{corr}(\mu,\sigma)$：

| Workload | corr(μ,σ) | Spearman | top-32 |
|---|---|---|---|
| **本实验实测** | **+0.04** | **0.9963** | **94%** |
| μ,σ 独立 | +0.02 | 0.9938 | 88% |
| 强反向 | −0.94 | 0.8799 | **53%** |
| 近乎完全反向 | −0.97 | 0.8109 | **41%** |
| 极端构造 | −1.00 | **−0.6338** | **0%** |

对应的真实场景：

| 类型 | μ | σ | 例子 |
|---|---|---|---|
| 长但可预测 | 高 | 低 | 定长翻译、"写 500 字…"、结构化生成 |
| 短但会爆 | 低 | 高 | 歧义提问、时而拒答时而长篇、会触发 reasoning 的问题 |

**生产环境里这种组合并不罕见**——翻译 API（长、稳定）和聊天端点（中位短、重尾）跑在同一个服务上。而 LMSYS 纯聊天任务类型同质，恰好落在 TIE 最无效的区域。

**注意 σ 整体放大无效**（2× 到 12× 都试过，Spearman 始终 ≥0.99），因为 2048 截断让 E[X] 和 CVaR 一起向上限饱和。

### 7.4 一个竞争性解释：采样次数——提出、测试、推翻

参考实现的 `compute_sample_weights()` 用绝对阈值上采样尾部。把阈值套到我的标签上：

| 阈值 | 他们给的权重 | 我的数据命中 |
|---|---|---|
| `logt_mu > 5.5` | 1.5 | **51.3%**（5,130 条）|
| `logt_sigma > 1.0` | 1.5 | **0.36%**（36 条）|
| `mu > 6.0 或 sigma > 1.3` | 2.0 | 40.4%（几乎全来自 μ）|

μ 的阈值在我的分布上合理，σ 的几乎不命中——没人会为 36 个样本写一条加权规则。**所以他们的 σ 分布比我的宽。**

**我提出的假设**：原因是采样次数。我用 20 次，传闻他们用 100 次。从重尾分布抽 20 个样本极端值大概率抽不到，MLE 的 σ 会系统性偏低。

**这个假设直接可测**，而且不用 GPU：把每条 prompt 的 20 个样本随机抽 5/10/15 个重新拟合，看 σ 怎么随 n 变化。

**结果（9,998 条全量）**：

| n | σ 均值 | σ 中位 | 相对 n=20 | Spearman(σₙ, σ₂₀) |
|---|---|---|---|---|
| 5 | 0.1166 | 0.0785 | −10.8% | 0.8189 |
| 10 | 0.1262 | 0.0908 | −3.4% | **0.9371** |
| 15 | 0.1290 | 0.0946 | −1.3% | 0.9744 |
| 20 | 0.1307 | 0.0967 | — | — |

用 $\sigma(n)=\sigma_\infty - c/n$ 拟合，预测值和实测值小数点后四位吻合：

$$\sigma_\infty = 0.1354,\quad c = 0.0941$$

> **n=20 已达渐近值的 96.5%；20 → 100 只能让 σ 均值涨 2.9%。**

**假设被推翻。** 而且排序几乎不受影响——样本砍掉一半，`Spearman(σ₁₀, σ₂₀) = 0.9371`。

**压缩效应只在极窄的一段成立**：

| σ 区间 | σ(10) 相对 σ(20) | 条数 |
|---|---|---|
| 低半 | −1.6% | 4,999 |
| p90–p99 | −3.1% | 900 |
| **top 1%** | **−11.7%** | **100** |

高端确实被压得更狠（top 10% 内部 Spearman 降到 0.7788）。但按同样的 $1/n$ 规律外推，即使对 top 1%，20→100 也只挽回约 9%——而 CVaR 项要起作用，需要打分乘子的离散度对抗 E[X] 的 48.5 倍跨度。

**所以这条路的结论是**：

1. **标签质量的两个解释都排除了**——随机噪声（分半信度 0.87）和采样不足（本测试）
2. σ R²=0.05 的剩余候选只有三个，**都没验证**：信号本来就不在 prompt 文本里（输出长度方差很大一部分来自解码随机性，我认为最可能）、数据规模（9,081 条唯一 prompt 对 184M 参数偏小）、架构
3. **他们 σ 更宽也不是采样次数造成的**。差别只能来自模型（他们示例用 Llama-3-8B，我用 Qwen3-8B）、采样参数、**或者我显式关掉了 Qwen3 的 thinking mode**——思考链长度本身高度不可预测，开着它 σ 会宽得多。这是推测，我没验证

**面试时怎么用这段**：这是一个完整的"读别人代码 → 发现异常 → 提出假设 → 当场可测 → 推翻自己"的闭环。结论本身（不是采样次数）不如这个过程重要。

### Q：你发现了什么规律？

**两条，都有数据验证。**

**规律一：过载时 FCFS 的等待是到达序号的线性函数**

$$W(i) = i\left(\frac{1}{\mu} - \frac{1}{\lambda}\right)$$

| 负载 | 分位 | 公式预测 | 实测 | 误差 |
|---|---|---|---|---|
| rate 16 | p90 | 44,421 ms | 41,475 ms | +7% |
| rate 32 | p90 | 71,764 ms | 68,590 ms | +5% |

**误差 4–11%。** 所以 p90 TTFT 从 rate 8 的 569 ms 跳到 rate 16 的 41,475 ms 不是异常，而是 ρ 跨越 1 的必然结果。

**规律二：交叉分位 $p^* = 100/\rho$**

过载时，一个到达窗口内最多只有 $1/\rho$ 比例的请求能"即到即走"。SJF 的收益正来自让这批短请求插队。因此：

> **SJF 只能改善低于 $p^*=100/\rho$ 的分位数，高于它的必然恶化。**

| 负载 | ρ | $p^*$ | p50 | p90 | p99 |
|---|---|---|---|---|---|
| rate 8 | 1.02 | 98 | −2.9% ✓ | −24.5% ✓ | +111.1% ✓ |
| rate 16 | 1.83 | 55 | −86.5% ✓ | +65.7% ✓ | +103.6% ✓ |
| rate 32 | 3.64 | 27 | −3.6% ✗ | +15.5% ✓ | +28.0% ✓ |

**9 个预测中 8 个成立。** 这解释了一个反直觉现象：**过载越严重，SJF 的优势越小**。rate 16 效果最戏剧化，正是因为 $p^*≈55$ 恰好落在中位数附近。

### Q：GPU 利用率怎么样？

我没有直接采样（疏漏），但可以从 TPOT 推 roofline：

| 量 | 值 |
|---|---|
| Qwen3-8B bf16 权重 | 16.4 GB |
| A100-40GB HBM 带宽 | 1,555 GB/s |
| 理论最短 step 时间 | **10.5 ms** |
| 实测 TPOT | **14 ms** |
| **显存带宽利用率** | **≈ 75%** |

验算：32 ÷ 14 ms = 2,286 tok/s，实测 2,237 tok/s，**误差 2%**。

**解码是显存带宽瓶颈，不是算力瓶颈**——每个 step 必须读一遍全部权重，与 batch 大小无关。所以 batch 32 时"读 16.4 GB 权重只产出 32 个 token"，SM 大部分时间在等内存。

外推：

| batch | 每 step 读取 | step 时间 | token 吞吐 | req/s |
|---|---|---|---|---|
| **32**（当前） | 18 GB | 14 ms | 2,237 | **8.8** |
| 512 | 42 GB | ~33 ms | ~15,500 | **~62** |

**我们把 7 倍的吞吐留在桌上没拿。**

## 8. 被 challenge 时的应答

### "你 batch size 只有 32，是不是实验设计有问题？"

**不要辩解，分两面说。**

> 32 是沿用论文作者的配置（它同时是 β 公式里的 B，必须一致）。我核验过它的性质：并发受**配置**而非显存约束，KV 利用率 2%，抢占 0 次。
>
> **好处**是排除了抢占这个混杂因素，各臂唯一的差异就是准入顺序。
>
> **代价**是同时排除了显存压力通路——调度通过降低 KV 占用提升并发与吞吐的机制。所以我测量的是"调度如何**重新分配**等待"，而不是"调度能否**减少**总等待"。论文报告的 2.3× 吞吐提升属于后者，在我的配置下**结构性地不可能复现**。
>
> 顺带，vLLM 官方默认是 128，作者调到了 32。batch 越小队列越早排满，调度器才有事可做——这是论文的一个承重假设。

### "论文说 100 RPS，你才 8.8，是不是你实现有问题？"

> 100 RPS 是**发起速率**，不是实际吞吐。用论文自己的 Table 3 反推：FCFS 跑完 3,000 条要 229.37 秒，**实际吞吐 13.1 req/s**。他们发 100 RPS、消化 13.1，过载 7.6 倍。我 rate 32 时实际 9.01 req/s，过载 3.6 倍——**同一个区间，只是标注方式不同**。
>
> 13.1 vs 8.8 的差距主要来自平均输出长度（由他们 Table 2 反推是 35–97 tokens，我的是 249）和硬件。

### "他们的 per-token latency 是 9 秒，你的 TPOT 是 14 毫秒，差 650 倍？"

> 那是两个不同的量。他们的是**归一化延迟** $E2E_i / N_i$，被排队时间完全主导。我用他们自己的数据交叉验证过——反推出的输出长度在五行里都自洽。
>
> 而且这个指标**在结构上偏袒 SJF 类策略**。分母是输出长度，让短请求等待会被放大惩罚，让长请求等待则被稀释。举例：两条请求，10 token 和 1000 token，各等 100 秒（FCFS）vs 短的不等、长的等 200 秒（SJF）——**总等待完全相同，归一化延迟差 50 倍**。
>
> 所以论文的收益应该拆成三部分：指标的结构性偏袒（纯指标效应）、等待的重新分配（守恒）、吞吐提升（真实，但需要显存成为约束）。

### "你的 σ 预测器 R² 只有 0.05，结论可信吗？"

> 这正是我设计 oracle 臂的原因。它用的是阶段一通过 20 次真实采样拟合的 σ，结果和预测 σ 完全一样（p50 差异在 −7.8% 到 +1.3%，噪声量级）。
>
> **所以 CVaR 项无效和预测器质量无关。**
>
> oracle 臂严格来说只排除了**预测误差**，没排除**标签偏差**——它用的还是我自己的标签。所以我单独测了标签：子采样重拟合显示 20 次采样已经达到渐近 σ 的 96.5%，加到 100 次只涨 2.9%，而且排序的 Spearman 是 0.937（见 §7.4）。**标签偏差这条路也堵上了。**
>
> 而且我有机制解释：E[X] 本身就是 σ 的增函数，SJF 已经隐式做了一阶风险规避；打分乘子的离散度只有 1.07–1.26×，而 E[X] 跨度 48.5×。

### "你怎么知道各臂真的在跑不同策略，而不是代码没生效？"

> 四条：
> 1. 服务日志里有 `[TIE] TIEScheduler active: queue=TIERequestQueue` 这类启动行
> 2. `popped_before_prediction` 在高负载下降到 0–6%，说明打分确实在影响调度
> 3. **p50 和 p99 反向移动**——p50 降 86.5%、p99 升 103.6%。这是 SJF 的特征签名，FCFS 不可能产生
> 4. FCFS 的三个分位挤在 24–48 秒（等待只取决于到达序号），SJF 从 3.3 秒铺到 98 秒，跨度 30 倍

## 10. 工程事故（讲故事用）

### 事故一：代理让健康检查永远不通

压测脚本等服务启动，120 次轮询全部失败，10 分钟后放弃。**但服务一直是好的**——日志里 `Application startup complete` 和我们调度器的心跳都在。

原因：集群设了 `http_proxy=10.99.0.130:3128` 但没设 `no_proxy`。curl 把 `localhost:8000` 也往代理上送，代理机到不了计算节点的 loopback。

**我自己的两个错误放大了它**：
1. `2>&1 >/dev/null` 把 curl 的报错全吞了，"代理超时"/"curl 不存在"/"服务真没起来"三种情况表现完全相同
2. 依赖了计算节点上不保证存在的 curl

**更要紧的是**：`vllm/benchmarks/serve.py:532` 用 `aiohttp.ClientSession(trust_env=True)`，**压测客户端也会走代理**。只修健康检查的话，60 条压测请求会在另一个地方失败，更难定位。

修法：导出 `no_proxy`、探活换成 Python + 空 `ProxyHandler`、失败时打印完整诊断。

### 事故二：僵尸服务冒充我们的服务

```
OSError: [Errno 98] Address already in use
```

端口 8000 被占，我们的 server 一启动就死。**但健康检查过了**——因为占端口的那个服务回了 200。

脚本于是报告 "server up"，然后压测客户端打到一个 engine 已死的进程上，每个速率空等 600 秒。

**根本错误在检查顺序**：

```python
for _ in range(180):
    if health_ok(): return 0          # 僵尸答应了
    if not process_alive(): ...       # 永远走不到这里
```

**先查健康再查进程存活。** 修法：端口改成 `8000 + job_id % 1000`、启动前预检端口、**先查进程存活再查健康**、清理时按命令行 `pkill` 兜底（`vllm serve` 的 engine 是子进程，杀父进程会留下孤儿）。

**这个事故的教训比 bug 本身重要**：即使没有端口冲突，只要我们的服务因任何原因启动失败、而节点上恰好有别的服务在那个端口，**实验就会静默地跑在错误的目标上，数据看起来完全正常**。这比崩溃危险得多。

### 事故三：默认配置删掉了逐请求数据

`vllm bench serve --save-result` 保存了聚合分位数，但 `serve.py:1489`：

```python
if not args.save_detailed:
    for field in ["input_lens", "output_lens", "ttfts", "itls", ...]:
        del result_json[field]
```

**删除发生在写文件之前。** 所以没加 `--save-detailed` 就拿不到逐请求数组，导致无法计算论文口径的 per-token latency 及其分位数。

## 13. 不许硬编的清单

下面这些我**不知道**，被问到就直说，然后讲我会怎么查：

1. **论文 Table 3 的 2.3× 吞吐提升机制**。我去读了作者公布的代码，结果是**公布的配置排除了我能识别的唯一机制**：

   - `start-server.sh` 里 `MAX_NUM_SEQS=32` 对**所有**策略生效，包括 FCFS——不存在"SDG 那组用了更大 batch"这个出口
   - 按他们自己的 `--gpu-memory-utilization 0.91` 和 `--max-model-len 8192` 算，8B（TP=1）的 KV 容量约 389k token、70B（TP=4）约 437k token，而 32 条请求**全部用满 8192 上下文**也只要 262k。**两种规模都装得下**，所以并发同样是配置约束，不可能因为换顺序而上升
   - 唯一的替代机制（抢占导致 prefill 重算）在这么大的显存余量下也不该频繁发生

   另外发现一个方法学问题：脚本里 `fcfs` 落到 `else` 分支拿到**全部** GPU，而 `ua`/`ssjf`/`ltr` 的 `TP_SIZE = GPU数 - 1`（留一张给预测器）。同一个设备列表下 FCFS 会多一倍模型并行度——这个方向对 TIE 不利，但脚本不自动配平，而实际调用方式没公布。

   **压测/SDG 的 harness 根本没在仓库里**（README 的结构只列了 `train/model_train.py` 和四个调度文件），所以无法进一步排查。**我没有确证，不编解释。**
2. **rate 32 时 SJF 的 p50 优势为什么几乎消失**。我排除了预测延迟（高负载下未打分比例 0–6%）和老化机制（衰减幅度不足以翻转 48 倍的分数差）。$p^*=100/\rho$ 规律预测它应该恶化，实测是持平，在噪声量级内。要定论需要逐请求数据。
3. **论文自己报告的 σ 预测精度**。我没下载到论文正文核对，所以不知道我的 R²=0.05 是"复现失败"还是"成功复现了一个已知难点"。
4. **他们的 σ 为什么比我的宽**。代码里有间接证据（`compute_sample_weights()` 把 `logt_sigma > 1.0` 当作值得上采样的群体，而这在我的标签上只命中 0.36%）。**采样次数这个解释我测过并排除了**——20 次已达渐近值 96.5%，加到 100 次只涨 2.9%（§7.4）。剩下的候选是模型不同、采样参数不同、或者我关掉了 Qwen3 的 thinking mode。**我倾向于最后一个，但没验证。**
